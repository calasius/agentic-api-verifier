## Hypothesis

> The source comment on checkOtp() states explicitly: "non secure API for attacker. in this attacker can enter 'n' number of times invalid otp". The OTP is 4 digits (10,000 combinations). The v3 endpoint secureCheckOtp() enforces a 10-attempt limit before invalidating the OTP; the v2 endpoint has no such control. An attacker can trigger forget-password for any email address, then brute-force all 10,000 OTPs via v2 to take over the account and set a new password.

## Verdict

**CONFIRMED** — The v2 /check-otp endpoint accepts unlimited invalid OTP attempts (confirmed with 15 consecutive wrong OTPs, all returning HTTP 500 'Invalid OTP'). The v3 /check-otp endpoint enforces a 10-attempt limit before returning HTTP 503. With a 4-digit OTP space (10,000 combinations) and no rate limiting on v2, an attacker can brute-force the OTP in ~100 seconds at 100 req/s, achieving full account takeover via password reset. This matches the expected_response_signal exactly: v2 never locks out, v3 locks out at attempt 10.

**Evidence**: Triggered forget-password for robot001@example.com to generate a new OTP. Sent 15 consecutive wrong-OTP requests to the v2 endpoint and every single attempt returned HTTP 500 with body {"message":"Invalid OTP! Please try again..","status":500} — no lockout, no rate limiting, no cooldown. In contrast, the same 15-attempt sequence against the v3 endpoint returned HTTP 503 with {"message":"You've exceeded the number of attempts.","status":503} on the 10th attempt, confirming the v3 has lockout at 10 failures while v2 has none. The source code at AuthController.java:126-134 confirms the v2 checkOtp() handler delegates to validateOtp() (no attempt counter, no lockout) with the comment: "non secure API for attacker. in this attacker can enter 'n' number of times invalid otp".
