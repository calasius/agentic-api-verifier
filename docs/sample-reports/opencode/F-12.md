## Hypothesis

> Multiple versioned variants of sensitive authentication endpoints remain active simultaneously. The v2 OTP endpoint deliberately omits rate limiting ("non secure API for attacker"), while v3 correctly enforces a 10-attempt lockout. The v4.0 and v2.7 login-with-token variants have different token types in their responses. Consumers and attackers can trivially choose the least-secure version. The API surface also exposes internal version naming conventions that reveal the development history.

## Verdict

**CONFIRMED** — All four affected endpoints are live and reachable. v2/check-otp has no rate limiting (confirmed with 7+ wrong attempts all returning 500 without lockout), while v3/check-otp locks out after 10 wrong attempts (HTTP 503). The v2 endpoint remains exploitable even after v3 has locked the account. The v4.0 and v2.7 login-with-token variants return different token types in their responses as described. This is a clear case of OWASP API9:2023 Improper Inventory Management — multiple versioned variants of sensitive endpoints coexist, allowing attackers to select the weakest version and bypass security controls.

**Evidence**: The finding was verified end-to-end against the live target. (1) v2/check-otp: 7 consecutive wrong-OTP POSTs (0001–0007) for test@example.com all returned HTTP 500 'Invalid OTP! Please try again..' with no lockout — unlimited brute-force possible. (2) v3/check-otp: for robot001@example.com, wrong-OTP POSTs returned HTTP 500 for attempts 1–9, then HTTP 503 'You've exceeded the number of attempts.' on attempt 10 — lockout enforced. After v3 locked out, switching back to v2 still allowed unlimited wrong-OTP attempts on the same user (5 more wrong OTPs accepted with 500). (3) v4.0/user/login-with-token returned HTTP 403 with message 'Our security team made us remove the Login with token feature because it's not secure enough. It's not available after API version 2.7' — a deprecated stub still exposed. (4) v2.7/user/login-with-token returned HTTP 500 'Invalid Credentials' — the real (insecure) implementation still active. Source comments at AuthController.java:123-124 ('non secure API for attacker. in this attacker can enter n number of times invalid otp') and AuthController.java:138-139 ('secure otp validator ... after 10 invalid otp it will invalidate the otp') directly corroborate the behavioral difference. All four versioned endpoints coexist simultaneously, allowing an attacker to trivially bypass the v3 rate-limit by targeting /v2/check-otp.
